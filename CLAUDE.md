# gnap-caep-risc

Server-side GNAP client. The crate is `gnap-caep-risc`. The public type is `Client`.

```rust
let client = gnap_caep_risc::Client::from_file("gnap.json")?;
let started = client.request_grant()?;
let done = client.finish_redirect(query, &[started.pending.as_ref().unwrap().id.clone()])?;
```

`Client::resolve` loads the same JSON keys as the Python and Node libraries. Methods are `from_file`, `request_grant`, and `finish_redirect`. Errors carry a code: `config`, `discovery`, `protocol`, `validation`, `signature`, or `ssf`.

## Tests

```bash
docker build --target test .
```

The `test` stage runs `cargo test` and then `cargo test --all-features` in `rust:1-bookworm`. GitHub Actions uses that command. Do not run Cargo on the host. The demo image does not run the suite.

Tests use an in-process stub on 127.0.0.1. They do not need a live authorization server.

`src/tests/stub_realm.rs` is the stub iya-sts realm for a `local` PEP (token, register, heartbeat, catalogue, policies, audit, PIP from a directory keyed by `uid`, the GNAP continuation DELETE). It uses only `std` and `serde_json`, so `src/tests/authzen.rs` and `src/bin/demo.rs` (by `#[path = "../tests/stub_realm.rs"]`) share it; `read_http` lives there and `ssf.rs` re-exports it. `src/bin/demo.rs`'s `mod tests::protected` (feature `local`, #41) drives `/attribute-protected` and `/orders/42` through `dispatch` with a `local` PEP holding `src/tests/demo_orders_policy.xml`, the XACML iya-sts stores for `orders_policy()`'s ALFA (the live `--pep` run requires the stored document to equal it; change both together): allowed (`attr1=abc123`, `acr`) 200/200, `attr1` other or absent 403 on the attribute page, `POST /orders/42` 403, no `acr` 403 on the order, signed out 401, each against `decide_grant(...).http_status()`.

The driver copies the checkout to a scratch context (no `.git`, `target`, `demo/generated`), runs the install script there, then builds the demo image, asserts the image's `/app/demo/generated` is exactly `tlsCa`'s chain, and runs it with only `client.key` and `client.crt` mounted and `TLS_CA_REFRESH=0`. It never fetches the CA for the demo, rewrites `tlsCa`, or mounts a CA. Its progress lines never print a URL or status from the signed-in client (CodeQL clear-text logging); secrets reach `docker run` as `-e NAME`. The install script never prints a password or secret: a generated test-user password goes to `demo/generated/<user>.password` (created 0600) and only that path is printed. Every `ssl` context in `scripts/` sets TLS 1.2 as the minimum.

The registrar passes over only a `set-custom-claim` refusal that says "not one of" (an iya-sts without the `gnap_access_token` claim set). Any other refusal fails.

The demo source is `src/bin/demo.rs`, ported from oidc-caep-risc-rust's feature/46-pep-stats demo and adapted to GNAP. Signed in, every page has a top bar with `site_nav` (Demo home, and with `pep` Attribute-protected and Order 42) and `user_menu` (avatar, name, **Sign in with another account**, **Sign out**; `menu.js` closes it on Escape or a click outside); sign-out is nowhere else. The name is `display_name`: `uid` (the `account` identifier's user part), else the assertion's `username`, else `preferred_username`, else the email, else `sub`. GNAP has no `prompt`, so another account is `POST /login/another`: it ends the sign-in (grant revoked, as `/logout`) and goes to `/?another=1`, which says iya-sts asks again only without a sign-on session (a POST and a same-origin redirect, so CSP `form-action 'self'` does not block a cross-origin redirect after a form). Three tabs, every block a `<details class="card pane" id=… open>` with a hidden Collapse all / Expand all toggle (`panes.js`):
- **Session** (`session_panes`): protections (key proof, key thumbprint by RFC 7638, instance id, interaction hash and nonce, binding, assertion, TLS, cache, stream), the subject and its verified assertion claims, the token cache (expiry, auto-rotation by `ensure_fresh` within 60 s on a page load, rotation count, manage and continuation held, access rights, `POST /session/rotate`), and the tokens: access, management and continuation access tokens by `token_fingerprint` (SHA-256, 8 bytes) and a JWT's decoded header and claims. No credential value is ever on a page; the raw ID token assertion is not kept by the library, so only its claims are shown.
- **CAEP & RISC events** (`events_panel`): the every-user warning pane, the stream with `POST /signals/verify`, the log (`LiveEvent`, at most 200); `app.js` polls `GET /api/signals?after=` (401 signed out); `GET /events` is 204 so its EventSource gives up.
- **Policy enforcement**: `pep_fragment` draws `pep_json` (the PEP's `status()`) as panes (Problems, Decisions, Cached policy, The PEP, Control plane, Try it), everything escaped, a `pep-none` pane without a `pep` section; `demo/public/pep.js` refetches `GET /pep-status.html` every 2 s, keeps closed panes closed and fires `panes-redrawn`; `GET /pep-status` is JSON; both 401 without a session.
`GET /attribute-protected` (feature `pep`) is `decide_grant` on `Access::new("read", "attribute-protected", "attr1")`: 401, 200, or 403 on a Deny or any PEP failure. Every page script is one IIFE (two top-level `const panel` stopped the later scripts loading); `styles.css` has `[hidden] { display: none !important; }`. Every page sends a CSP with `connect-src 'self'` and `cache-control: no-store`. Its tests are `src/bin/demo.rs`'s `mod tests`. `.gitignore` ignores `/bin/` at the root only, so the demo is tracked.

`scripts/configure_iya_sts.py` gives the test user `attr1=abc123` (`set_test_attribute`): it defines the realm's custom attribute with a second token (`admin:read admin:security`, minted for that call alone; iya-sts seeds `sts-api-client` in `SECURITY_ADMIN`), tries the value either way, and prints what a Security Administrator does only when the definition was refused and the value cannot be set. `orders_policy` has `readAttributeProtected` (target `attr1 == "abc123"`, `urn:sts:xacml:attribute:attr1`, subject category). `src/tests/install_script.rs` runs those parts in python3 against a recording stand-in for `/admin-api`.

## tlsCa, the iya-sts trust chain

`tlsCa` (demo default `generated/idp-ca.pem`) is the iya-sts TLS listener CA trust chain. `scripts/configure_iya_sts.py` writes the whole chain there on every run through `scripts/trust_chain.py`'s `save_trust_chain()` (`GET /tls/server-certificate`, falling back to the handshake) and prints the anchor's subject and SHA-256. The Dockerfile's final stage runs `COPY demo demo` after the binary is built (the `build` stage copies only `Cargo.toml`, `Cargo.lock` and `src`, so a new chain does not recompile), and `.dockerignore` admits only `demo/generated/idp-ca.pem` from `demo/generated`. Copying the directory, not the file, keeps a build without the chain working; a file or glob COPY fails. Rebuild the demo image after re-running the install script against another iya-sts. The start-time refresh (`scripts/trust_chain.py` in `CMD`) stays, and `TLS_CA_REFRESH=0` turns it off.

`src/http.rs` `Pinned` reads every PEM block of `tlsCa` as an anchor. The exact-match shortcut compares only the presented LEAF with the file's certificates (never any presented certificate with any file certificate: CA certificates are public) and still checks the name; otherwise webpki verifies the chain to an anchor and the name. `src/tests/trust_chain.rs` covers the script writing the chain, the library taking the file, every block as an anchor, a forged leaf before the real CAs refused, and the right chain with the wrong name refused. Every `ssl.SSLContext` the scripts make sets TLS 1.2 as the minimum.

## Embedded PEP

#39 (iya-sts#1206 work item 8), behind the `pep` feature (`local` adds the engine): `src/pep.rs` wires in the shared `iya-pep` crate (rcbj/iya-pep-rust), following oidc-caep-risc-rust#46.
- `resolve` builds the PEP (nothing sent) from the `pep` section and stores it on `Config.pep`; `Client::create` (and `from_file`) starts it. `Client::new` does not.
  - `pdpUrl` defaults to the grant endpoint's realm (`/realm/<id>` kept, a named server's segment and `/gnap` dropped; else the origin). Not `idTokenIssuer`, which defaults to the origin and drops the realm.
  - `application` defaults to `application`; `signals` to whether the library runs a receiver (`ssf` resolved); `tlsCa` to the library's; `assertionKey` is relative to the config's directory.
  - It refuses an assertion key that is the client instance key (by JWK thumbprint). That is the only key this library holds (the mTLS certificate is the same key).
- Without the feature, a `pep` section is refused rather than ignored.
- `decide` / `decide_grant` adapt a `Person` (`uid` from `account`, else the assertion's `username` claim (iya-sts's own, on every ID token), else `preferred_username`, else `sub`; the ID token claims) into the PEP's subject. `decide_grant` denies without asking a grant with no subject, one this client revoked (`revoke` remembers the continuation URI, 10000 at most), or one whose access token expired.
- `ReceiverOpt::pep`: `SignalsReceiver::new` adds `pep-policies-changed` to the events requested and registers the hand-over when the PEP wants events (`local`, or `central` with a Permit cache).
- `src/tests/pep.rs` has its own stub PDP (also the realm's GNAP continuation URI), and reuses `src/tests/ssf.rs`'s transmitter for the receiver test. The no-feature refusal is in `src/tests/config.rs`.
- **The dependency is a git dependency on iya-pep-rust's `feature/1`** until that crate's first release. Switch it to the crates.io version then, because crates.io refuses a git dependency at publish.
- **The lock pins iya-pep `43eaf26`** (feature/1): `Decision::http_status()` (200 for a Permit, 403 for Deny and Unavailable), which the demo's `/orders/<id>` and `/attribute-protected` take their status from; a panic while deciding is `Unavailable`; `central` drops every cached Permit on a failed evaluation or heartbeat, and serves none until the service answers an evaluation again. Every PEP failure is a 403 (the owner's rule). Since `d88edef`: a `pep` section with no `mode` is `local` (a `pep`-only build refuses it), the poll period follows the event-stream state, and with signals on a PEP starts as `EventStream::Down` until the receiver reports its stream. `src/tests/pep.rs`'s sections name `central`, which they were written for; `a_section_without_a_mode_is_local` holds the default. The TLS features (`native-tls` default, `rustls`) are left as they were.
- The live test of the PEP (`live_iya_sts.py --pep`) needs iya-sts #2026–#2028, which `main` lacks, so the nightly runs without it. The committed `demo/gnap.json` has no `pep` section; `configure_iya_sts.py --pep` writes one (never commit the written configuration or `demo/generated`).
- oidc-caep-risc's live run (its #46) found two defects; both are held here by `src/tests/pep.rs`. `Client::from_file` keeps the `pep` section (`from_file_keeps_the_pep_section`; `read_file` always passed the whole document to `resolve`). A reused poll stream gets the event types it lacks PATCHed in (`with_requested_events`); a refusal goes to `ReceiverOpt::on_error` (new: it also takes the receiver's other error lines, which still print to standard output without it), and `start` tells the PEP `set_event_stream(Requested)` or `Excluded` from the stream's events, which the heartbeat reports as `policyEvents` (`a_reused_stream_gets_the_policy_event_added`, with PATCH on `src/tests/ssf.rs`'s transmitter).
- The receiver keeps reporting its stream's health to the PEP (after oidc-caep-risc-rust 126b4ad): `Requested`/`Excluded` at `start` and after every good poll, `Down` after a failed poll (the PEP polls its own policies then) and on `stop()`. `the_peps_stream_state_follows_the_polls` holds it, with `poll_status` on the stub transmitter failing its polls.

Offline, `the_table_decides_as_expected_in_local_mode` runs every case through a `local` Client against a stub realm per PEP group (policies from each policy's `xacml`, the catalogue, the directory as the PIP). A case marked `localDefect` must still give that wrong local answer, so the mark comes off when iya-pep is fixed; the live run ignores the mark. ## Layout

- `src` the client, key proofs (mtls, httpsig, jwsd), and one poll stream
- `src/tests` config, subject, client, the Shared Signals receiver, the install script's attribute and policy steps, and (feature `pep`) the embedded PEP
- `src/pep.rs` the embedded iya-sts PEP (feature `pep`)
- `src/bin/demo.rs` the HTTP demo; `demo/gnap.json` the sample configuration
- `scripts/configure_iya_sts.py` registers the app; `scripts/redirects.py` and `scripts/trust_chain.py` support it

## Signals

Subjects (#43): `ReceiverOpt::add_subjects` / `ssf.addSubjects` (default true, refused unless boolean) makes the receiver tell the transmitter who is signed in, so a stream carries only those people (the owner's rule; iya-sts#2234; correct also against `default_subjects: NONE`).
- `track` calls Add Subject (`add_subject_endpoint`, body `stream_id`, `subject`, `verified: true`) for a person not yet accepted. The subject is `iss_sub` with the transmitter's `issuer`, else `email`. Before `start`, `start` adds every tracked person.
- `untrack`, and an event that ends a sign-in (on the poll thread), call Remove Subject when no other tracked sign-in maps to the same subject and the subject is in `Inner.added`. Re-tracking a `local_id` neither adds nor removes.
- The calls are inline (no timer). A refusal or failure is reported once to `on_error` with only the subject format, never retried, never fatal. No endpoint, no call.
- A receiver whose PEP wants events (`Shared.pep`) adds `{format: opaque, id: pep.config().application}` at `start`, before the tracked people, and never removes it. iya-sts narrows a stream that names subjects to those subjects, and `pep-policies-changed`'s subject is complex with that `application` member (iya-sts `applicationSubject()`; GNAP's scope lets it through, #2028). Without it the first sign-in cut the local PEP off from its events (found live by wsfed-caep-rust, 5257f07). `a_receiver_adding_subjects_names_the_application_its_pep_hears_about` holds it. Live `--pep` against `iya-sts:local` after this: the flip came `via: event` in 1.1 s.
- An expired session dropped by `Index::find` is not removed at the transmitter.
- Tests: `src/tests/ssf.rs` (`subject_endpoints`, `subject_calls`, `subject_status` on the stub transmitter) and `add_subjects_defaults_on_and_takes_only_a_boolean`.
- `start_transmitter` makes the stub's RSA keys first (`warm_keys`): generating them lazily under a parallel debug suite took longer than the receiver's 15 s timeout on `/jwks`.
- The demo tracks every sign-in (`watch` tracks into a running receiver; before #43 only the first was tracked).

Omitted or `true` keeps CAEP and RISC on, and the resolved configuration omits `signals`. `false` does not start the receiver, does not require transmitter metadata, drops `ssf.read` and `ssf.manage`, and is kept on the resolved configuration. Anything else returns `signals must be true or false`. `SignalsReceiver::stop` waits until the background poll has finished.
